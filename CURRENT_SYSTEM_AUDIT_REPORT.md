## Executive summary

The nine findings in `POST_CUTOVER_AUDIT_REPORT.md` now have focused regression
coverage. The complete suite passes with 49 tests, and compilation, formatting,
migration-drift, and Git whitespace checks are clean.

The new Systemwide SOP admission gate is not yet a system-wide invariant. It is
enforced by `SpruceGoose.CLI.Executor` before the canonical CLI starts a task,
but it is absent from the public Ash `Task.transition` action. Any in-process
caller that invokes that action directly can move a ready task to
`in_progress` without verifying the stored SOP digest. Public create and
acknowledgment actions also accept the gate fields, including the exemption
flag and acknowledgment timestamp, from callers.

The current tree should therefore not describe the SOP gate as a hard domain
control. The CLI path is guarded, but the resource boundary is not.

## Findings

### CSA-01 — High: direct task transition bypasses the SOP gate

The CLI executor calls `SopGate.verify/1` when it handles a
`ready -> in_progress` transition. The public Ash `:transition` action itself
does not call that verification. Existing tests also invoke the transition
action directly, confirming that it is an intended callable domain interface.

Evidence:

- `lib/spruce_goose/cli/executor.ex` performs `SopGate.verify(task)` inside
  `require_transition_preconditions/2`.
- The same module later invokes the public `:transition` action.
- `lib/spruce_goose/workflows/task.ex` validates lifecycle, board-column,
  cancellation-reason, diagnosis-evidence, and TODO rules, but does not verify
  the SOP digest.
- Tests call `Ash.update(task, ..., action: :transition)` directly.

Impact:

- an in-process caller can start a gated task without reading the SOP;
- a stale acknowledgment can be accepted outside the CLI;
- the README's statement that start requires a current acknowledgment is only
  true for the CLI adapter, not for the domain action.

Remediation:

1. Move SOP verification into a Task transition change or validation that runs
   for every `ready -> in_progress` update.
2. Keep the CLI check only as an optional early error path.
3. Add a regression test that corrupts `sop_digest`, then asserts a direct
   `Ash.update(..., action: :transition)` fails.
4. Test both CLI and non-CLI transition callers against the same invariant.

Acceptance criteria:

- no public Task transition path can enter `in_progress` with a missing or stale
  required acknowledgment;
- grandfathered tasks with `sop_gate_required = false` remain explicitly
  covered by a migration/compatibility test.

### CSA-02 — Medium: SOP gate evidence and exemption state are caller-writable

The public Task create action accepts `sop_gate_required`, `sop_path`,
`sop_digest`, and `sop_acknowledged_at`. The public `:acknowledge_sop` action
accepts the same fields. The resource validation checks shape and canonical
path, but it does not prove that the digest came from the file or that the
timestamp was generated by the trusted acknowledgment operation.

The database constraint deliberately permits `sop_gate_required = false` for
grandfathered/imported rows. Because the public actions accept that flag, the
compatibility mechanism is also a caller-selectable exemption.

Impact:

- direct callers can create exempt tasks;
- direct callers can write fabricated acknowledgment timestamps;
- direct callers can supply a well-formed digest without using
  `SopGate.acknowledge/1`;
- audit evidence does not establish that acknowledgment occurred through the
  trusted path.

Remediation:

1. Remove SOP gate fields from general public create/update acceptance.
2. Populate required acknowledgment fields in a trusted change that reads and
   hashes the canonical SOP.
3. Restrict the exemption to a private import/grandfathering action or a
   migration-only path.
4. Add tests showing ordinary callers cannot set `sop_gate_required = false` or
   manufacture acknowledgment evidence.

### CSA-03 — Medium: the canonical SOP path is bound to one host layout

The application module and database check constraint both embed:

`/home/admin-papa/.openclaw/vaults/openclaw-system/10-sop/Systemwide SOP.md`

The application cannot run under another account or filesystem layout without
a coordinated code and schema migration. A path change also prevents existing
rows from being refreshed until the constraint is changed.

Impact:

- deployments are tied to one host account and directory structure;
- development, test, recovery, and future host migration require that private
  layout;
- changing the canonical location is an application-plus-database migration,
  not an operational configuration change.

Remediation:

1. Resolve the canonical SOP location from validated runtime configuration.
2. Store a stable SOP identifier plus digest in task evidence, rather than
   enforcing a host absolute path in a database constraint.
3. Fail startup or admission clearly when the configured SOP is absent.
4. Test an alternate configured path and a path migration.

## Recommended remediation order

1. Fix CSA-01 before representing the SOP gate as enforced system-wide.
2. Restrict gate evidence and exemptions as described in CSA-02.
3. Remove the host-bound path contract in CSA-03 before deployment portability
   or recovery is required.
4. Add the adversarial direct-action tests, rerun all checks above, and append
   remediation evidence to this report.

## Final assessment

The post-cutover authority and Kanban hardening is materially stronger and all
current automated checks pass. The new SOP feature is a useful CLI admission
check, but it is not yet a trustworthy domain invariant because callers can
bypass verification and can write its evidence fields directly.

Production use of the existing authority and Kanban model is supportable under
the passing regression suite. Production reliance on the SOP gate as a
system-wide control should remain blocked until CSA-01 and CSA-02 are resolved.
